# مصروف

**اللغات:** [English](README.md) | **العربية**

مصروف هو تطبيق أندرويد محلي لإدارة المصروفات الشخصية، يحوّل رسائل البنوك المدعومة إلى سجل مالي منظم.

يركز المشروع على **الصحة المالية، وقابلية التتبع، والاسترجاع الآمن**. يحتفظ التطبيق برسالة SMS الأصلية كدليل، ويفصل بين فهم الرسالة وتسجيل الحركة المالية، ويترك الحالات غير الواضحة للمراجعة بدل التخمين، ويحافظ على حالات إعادة المحاولة عند حدوث فشل بدل فقدان العملية بصمت.

## ماذا يفعل مصروف؟

يستطيع مصروف:

- التقاط رسائل البنوك المدعومة عند وصولها مباشرة أو من سجل الرسائل القديم؛
- تصنيف الرسائل المالية وغير المالية؛
- إنشاء حركات مالية للمشتريات، والدخل، والتحويلات، والاستردادات، والرسوم، والسحب النقدي، وسداد البطاقات، وغيرها من الأنواع المدعومة؛
- متابعة الحسابات والبطاقات والقروض المملوكة للمستخدم؛
- ربط رسالتي التحويل البنكي كحركة واحدة عند وجود دليل كافٍ، بدون عد المال مرتين؛
- إبقاء الحالات غير المؤكدة في المراجعة؛
- حساب ملخصات الحسابات والبطاقات والتجار والالتزامات والفترات المالية؛
- الحفاظ على تصحيحات المستخدم وقرارات المراجعة؛
- استخدام دليل سعر الصرف المناسب زمنيًا وعدم تطبيق سعر مستقبلي على عملية قديمة؛
- إنشاء نسخ احتياطية مشفرة واستعادتها بأمان؛
- مقارنة السجل المستنتج من الرسائل مع **كشف حساب بنكي** يقدمه المستخدم، بدون تعديل السجل المالي تلقائيًا.

الدعم البنكي الخاص بالرسائل يركز حاليًا على **بنك الجزيرة**. المعمارية تسمح بإضافة بنوك أخرى، لكن لا يُعتبر أي بنك مدعومًا قبل إضافة كشف المرسل، واختبارات الرسائل، وعقد Adapter الخاص به.

## كيف يعمل التطبيق؟

المسار المالي الأساسي:

```text
رسالة SMS
    ↓
RawSms
    ↓
ParsedEvent
    ↓
تحديد الملكية / الإسناد
    ↓
Reconciliation
    ↓
FinancialTransaction أو Review
    ↓
Dashboard
```

### مسار الرسالة المباشرة

```text
IncomingSmsReceiver
→ LiveSmsIntake
→ CaptureBankSmsUseCase
→ RawSms محفوظة
→ WorkManager
→ LiveSmsProcessingWorker
→ ProcessStoredSmsUseCase
→ Parsing
→ Ownership
→ Reconciliation
→ Review / Ledger
```

يتم تمرير معرف `RawSms` فقط إلى WorkManager. نص الرسالة المالية نفسه لا يوضع داخل Work input.

### مسار الرسائل التاريخية

فحص الرسائل القديمة له مسار مستقل:

```text
HistoricalSmsScanner
→ HistoricalSmsBatchProcessor
→ تحليل كل رسالة
→ مرور واحد للملكية والمطابقة والمراجعة على الدفعة
```

لا يتم إنشاء Worker منفصل لكل رسالة تاريخية.

## قواعد الصحة المالية

يعامل مصروف القواعد التالية كقواعد معمارية أساسية:

- **RawSms دليل أصلي غير قابل لإعادة الكتابة.**
- كل رسالة مالية معروفة يجب أن تنتهي كعملية **مسجلة، أو بحاجة إلى مراجعة، أو محفوظة لإعادة المحاولة**.
- وجود `ParsedEvent` لا يعني أن الحركة المالية تم تسجيلها بنجاح.
- فشل المطابقة لا يُعتبر نجاحًا بصمت.
- لا يجوز ربط رسالة RawSms بأكثر من حركة مالية مسجلة واحدة.
- التحويل بين حسابات المستخدم يمثل حركة واحدة، وليس مصروفًا ودخلًا منفصلين.
- التحويلات المتشابهة في المبلغ تبقى مستقلة ما لم يوجد دليل يثبت أنها نفس الحركة.
- قرارات المستخدم الصريحة لها الأولوية على الأتمتة اللاحقة.
- لا يتم جمع العملات المختلفة معًا بصمت.
- الـDashboard يقرأ حقائق منظمة محفوظة ولا يعيد تفسير نص الرسالة البنكية.

## الحسابات والبطاقات والهوية

الهويات المالية مرتبطة بالبنك.

أمثلة:

```text
account:BANK_ALJAZIRA:3001
card:BANK_ALJAZIRA:7271
```

آخر أربعة أرقام متشابهة في بنكين مختلفين لا تعني أن الحساب أو البطاقة واحد.

كذلك يتم الفصل بين التدفق النقدي للحساب البنكي ونشاط البطاقة الائتمانية. مثلًا: الاسترداد إلى الحساب البنكي يزيد النقد في الحساب، بينما الاسترداد إلى البطاقة الائتمانية يقلل نشاط/التزام البطاقة ولا ينشئ نقدًا في الحساب الجاري.

## التحويلات

مطابقة التحويلات تتم بشكل محافظ، وقد تعتمد على:

- مرجع العملية البنكية؛
- الحساب المصدر والوجهة مع هوية البنك؛
- توقيت العملية البنكي؛
- وقت استلام الرسالة عند الحاجة؛
- المبلغ والعملة بشكل دقيق؛
- دليل ملكية الحساب.

إذا كان هناك أكثر من مرشح متساوٍ، يبقي مصروف العملية في المراجعة بدل التخمين.

## العملات الأجنبية

تحويل العمليات بالعملات الأجنبية يعتمد على دليل متاح **في وقت العملية أو قبله**. لا يتم استخدام سعر صرف وصل لاحقًا لشراء أقدم.

الأسعار المحفوظة لا تتغير بصمت. أي تصحيح لسعر تاريخي محفوظ يمر عبر مسار تصحيح صريح.

## النسخ الاحتياطي والاستعادة

النسخ الاحتياطية المحمولة مشفرة ومصادق عليها.

مسار الاستعادة مصمم للفشل الآمن:

- يتم رفض الملفات التالفة أو الضخمة قبل استبدال قاعدة البيانات الحية؛
- النسخ القديمة غير المشفرة تحتاج موافقة واضحة؛
- عند توقف الاستعادة في المنتصف يتم الرجوع لقاعدة صحيحة أو إكمال النسخة الجديدة بالكامل؛
- يتم تشغيل migrations وفحوص سلامة قاعدة البيانات قبل اعتماد النسخة المستعادة؛
- يتم تنظيف ملفات staging المتروكة من عمليات سابقة.

النسخ السحابي التلقائي لحالة البيانات المالية المنظمة معطل. إنشاء النسخة المحمولة يتم بطلب صريح من المستخدم.

## مطابقة كشف الحساب البنكي

يحتوي مصروف على مقارنة اختيارية، للقراءة فقط، بين السجل المالي المبني من SMS وبين **كشف حساب بنكي** يختاره المستخدم.

الصيغة الحالية المدعومة هي CSV منظم ومتحقق منه، يحتوي على:

- البنك والحساب بشكل صريح؛
- فترة تغطية واضحة؛
- اتجاه العملية Debit/Credit؛
- المبلغ والعملة بدقة؛
- تاريخ/وقت القيد؛
- مرجع العملية اختياريًا.

نتائج المقارنة:

- **MATCHED** — الحركة موجودة ومتوافقة في الطرفين؛
- **STATEMENT_ONLY** — الحركة موجودة في كشف البنك ولكن مصروف لم يسجلها؛
- **LEDGER_ONLY** — مصروف يحتوي حركة لا تظهر في كشف الحساب خلال نفس الفترة؛
- **AMBIGUOUS** — يوجد أكثر من تطابق محتمل ولا يمكن الجزم بأمان؛
- **UNSUPPORTED** — الأدلة المتاحة لا تكفي لإجراء مقارنة آمنة.

المقارنة لا تنشئ ولا تحذف ولا تخفي ولا تعيد تصنيف العمليات تلقائيًا.

الميزة الحالية تستهدف **كشف الحساب البنكي**، وليس كشف البطاقة الائتمانية.

## نموذج الخصوصية

مصروف Local-first:

- معالجة SMS والبيانات المالية تتم على الجهاز؛
- كشف الحساب يُقرأ محليًا ويبقى مؤقتًا لغرض المقارنة؛
- نص كشف الحساب الخام لا يتم رفعه بواسطة ميزة المطابقة؛
- السجلات لا يجب أن تحتوي نصوص SMS أو أرقام الحسابات أو PIN أو كلمات المرور أو tokens؛
- بيانات GitHub الخاصة بالتحديثات محمية باستخدام Android Keystore.

## هيكل المشروع

```text
app/src/main/kotlin/com/baraa/masroof/
├── application/   تنسيق العمليات وWorkflows
├── bank/          Adapters وتحليل الرسائل الخاصة بكل بنك
├── core/          أدوات ومكونات منخفضة المستوى
├── data/          Room وPreferences وتنفيذ Repositories
├── domain/        النماذج والقواعد والمطابقة والعقود
├── parsing/       نماذج وقواعد التحليل العامة
├── presentation/  واجهات Compose وViewModels
└── sms/           حدود Android SMS وأدوات الرسائل
```

مواقع مهمة أخرى:

```text

docs/                                توثيق المعمارية والقرارات التاريخية
scripts/                             أدوات CI والإصدار واختبارات process-death
.github/workflows/                   CI وعمليات الإصدار
```

## حدود المعمارية

اتجاه الاعتماد مقصود ومقيد:

```text
presentation
    ↓
application
    ↓
domain / parsing / data / sms / bank
```

أي منطق متعلق بصياغة رسائل بنك معين يجب أن يبقى داخل `bank/*`. الـDashboard لا يستورد parsers البنوك ولا يعيد تحليل نصوص الرسائل.

للقواعد الهندسية الكاملة راجع [AGENTS.md](AGENTS.md).

## Migrations قاعدة البيانات

ملفات Room migrations وملفات schema القديمة جزء من التوافق مع المستخدمين الحاليين، ولا تُحذف لمجرد أنها تخص إصدارات قديمة.

أي تغيير على schema يجب أن يتضمن:

1. Room migration؛
2. تحديث entity/mapper؛
3. تعبئة بيانات parser عند الحاجة؛
4. اختبار migration؛
5. backfill عندما تحتاج البيانات القديمة لحقائق جديدة قبل عرضها بأمان.

## الاختبارات

أوامر محلية مفيدة:

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:lintDebug
./gradlew detekt
./gradlew :app:assembleDebug
```

CI يشغل كذلك اختبارات Emulator لمسارات lifecycle والاستعادة. اختبارات قتل العملية الحقيقية تستخدم:

```bash
bash scripts/m13-process-death.sh
```

اختبارات Golden Ledger وFinancial Invariants تحمي إجماليات الأموال، روابط RawSms، حالات Review، retries، حيادية self-transfer، فصل العملات، وسلوك replay.

## إرشادات التطوير

قبل تعديل أي سلوك مالي:

1. أعد إنتاج الحالة باختبار أو fixture محدد؛
2. حافظ على RawSms الأصلية؛
3. أبق منطق صياغة البنك داخل parser البنك؛
4. لا تتجاوز بوابات parse-status أو ownership؛
5. اجعل reconciliation idempotent؛
6. حافظ على قرارات المستخدم؛
7. أضف migration/backfill إذا تغير التخزين؛
8. شغل الاختبارات المستهدفة ثم CI المناسب.

لا تحذف ملفًا لمجرد أن اسمه يبدو قديمًا. بعض العناصر التاريخية مقصودة، مثل Room migrations، توافق backup، regression fixtures، process-death hooks، وتوافق saved navigation.
